# Canonical notebook execution

The canonical source is `notebooks/canonical.ipynb`, generated by `scripts/build_notebook.py`. It pins source revision `4cc77325af2e4bebba1de4f30f489db72ea35478` and verifies individual module/requirements hashes before importing code. The model is independently verified against SHA-256 `d41c82a2a2310791ff234bc784f765d7b986bf569990ac32a25206c8153f6518`.

## What runs

The default notebook downloads or locates the checkpoint, audits all official inputs and split hashes, displays a calibration example, checks the metric/RLE contracts, runs CPU inference on all 180 test images, validates every output mask and coverage entry, and writes a proof record. It does not retrain or submit automatically. Training and repeat holdout evaluation have explicit switches and explanations. The reported original holdout is already exposed.

On Kaggle, input data is attached through the competition source in `notebooks/kernel-metadata.json`. The output directory is `/kaggle/working/solarseg-run/`; its useful files are `submission.csv`, `submission.images.json`, `submission.validation.json`, and `notebook-proof.json`. Generated probability caches are removed after successful serialization. Locally, outputs go to `artifacts/notebook-run/`.

## Why an isolated kernel

Kaggle notebook version 1 installed pinned packages inside a live, preloaded Python environment. It failed during SciPy import because the in-memory NumPy extension and the newly installed Python files differed (`_blas_supports_fpe` missing). No cloud predictions were produced in that run. This was an environment failure, unrelated to the scored local submission.

Version 2 introduced kernel isolation but failed because Kaggle's Debian Python lacks working `ensurepip`. Version 3 creates a virtual environment under `/tmp` with `--without-pip`, then uses the host's `pip --python <venv-python>` to install CPU PyTorch from its official index and the repository's exact requirements. This is pip's [documented support for a pip-less environment](https://pip.pypa.io/en/stable/topics/python-option/). It starts a fresh kernel using that interpreter. Each readable `%%solarseg` cell sends its body to the same persistent kernel. Jupyter forwards the child's cell outputs; any execution error fails the enclosing cell. The original Kaggle kernel's numerical packages are not modified. The CPU build's `+cpu` suffix is recorded alongside the pinned base version.

This uses Jupyter's documented [kernel messaging protocol](https://jupyter-client.readthedocs.io/en/stable/messaging.html) and [interactive execution API](https://jupyter-client.readthedocs.io/en/stable/api/client.html). CPU wheels come from [PyTorch's official installation index](https://pytorch.org/get-started/locally/).

## Local replay and publication

Install the repository environment and register `python -m ipykernel install --user --name solarseg`. Then run:

```bash
python scripts/replay_notebook.py
```

To exercise the same child-kernel transport locally, using the already installed pinned interpreter:

```bash
SOLARSEG_ISOLATE=1 SOLARSEG_ISOLATED_PYTHON="$PWD/.venv/bin/python" \
  python scripts/replay_notebook.py
```

The wrapper saves the executed notebook, checks its output against the independently generated selected submission, and records notebook/module/checkpoint hashes. A reused probability cache is not fresh inference; remove only that generated cache before making a fresh-inference claim. Keep the original submission's replay record as historical evidence when changing notebook orchestration.

For the repository owner, publish the reviewed notebook using the authenticated CLI:

```bash
kaggle kernels push -p notebooks --timeout 7200
kaggle kernels status srivatsavkannan/solar-filaments-canonical-baseline-2026
```

Other users should copy the metadata and change its owner/slug before publishing. Kernel publication does not upload a competition CSV. Check the kernel's completed status and output proof separately from the Kaggle submission receipt.
